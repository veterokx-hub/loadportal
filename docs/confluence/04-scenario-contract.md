# Контракт сценария

Полная таблица полей: `docs/domain-model.md`. Идентификаторы прогона: `docs/data-model-ids.md`. Здесь — как этим пользоваться при доработке.

## Где живёт сценарий

| Место | Что это |
|---|---|
| Браузер, `localStorage` `ltp-state-v1` | Черновик, пока пользователь не сохранил сборку |
| `build_records.scenario_json` | Снимок на момент сохранения. Отдельной таблицы сценариев нет |
| Тело запроса генератору | Тот же JSON, snake_case |

Jackson в Java пишет camelCase записи как snake_case (`spring.jackson.property-naming-strategy: SNAKE_CASE`).

## Состав

`name`, `source_type` (`openapi` | `postman`), `base_url`, `load`, `datasets[]`, `requests[]`, `autostop`, `prometheus`.

Запрос: `id`, `order`, `name`, `method`, `path`, `url`, `headers`, `params`, `extractions`, `intensity`, `validation`, `dataset_id`, `repeat`.

`url` если задан, заменяет `base_url` + `path`.

`path` и тело могут содержать `{name}`. Это плейсхолдер портала. Его закрывает параметр с тем же именем. `${name}` в тексте — уже переменная движка, портал её не вырезает как плейсхолдер.

## Параметр

`name`, `location` (`path` | `query` | `header` | `body`), `source`, `required`.

Источник:

| kind | Смысл |
|---|---|
| `constant` | Текст как есть. Внутри может быть `${var}` |
| `generator` | `uuid`, `randomInt`, `randomString`, `counter`, `timestamp` |
| `correlation` | Прочитать переменную `source.variable`, которую кто-то уже создал |
| `csv` | Взять ячейку колонки `source.column` |

Имя параметра Query и Header уходит в HTTP как ключ. Само по себе оно не становится переменной скрипта. Исключения: счётчик (имя параметра — переменная во всех трёх движках) и случайная строка в Gatling. См. [Переменные скрипта](05-script-variables.md).

Path-параметр портал создаёт из `{name}` в адресе. Имя в UI не редактируется, задаётся только источник значения.

## Извлечение

`variable`, `type` (`json` | `regex` | `boundary`), `expression`, `match_no`, `default_value`.

Всегда создаёт переменную скрипта с именем `variable`. Срабатывает после ответа, поэтому в тот же запрос не подставляется. Корреляция на это имя имеет смысл в запросе ниже по порядку.

## Датасет

`id`, `name`, `file_name`, `columns`, `rows`, `random`.

Колонка становится переменной скрипта. В текущих генераторах имя переменной — заголовок колонки, не имя параметра, который колонку выбрал. Все колонки привязанного датасета попадают в фидер JMeter и в сессию Gatling, даже если параметр выбрал одну.

Общий `dataset_id` у запросов склеивает их в одну группу нагрузки вместе с явной корреляцией.

## Нагрузка

`load.test_mode`: `ramp_hold` или `max_search`.

Целевой RPS лежит на запросе: `intensity.target_rps`. Это HTTP-запросы в секунду. k6 и Gatling делят его на число HTTP за итерацию группы. JMeter держит профиль Throughput Shaping Timer и из `assumed_latency_sec` оценивает пул потоков.

`repeat` — сколько раз запрос повторяется внутри одной итерации. Минимум 1. Счётчик JMeter и k6 за эти повторы не тикает: одно значение на итерацию потока.

## Проверки ответа

`validation.check_response_code`, `expected_status`, `response_contains`.

Это не quality gate пайплайна. Gate считается отдельно, по файлам на поде генератора.

## Группировка

Запросы одной группы исполняются одним сценарием виртуального пользователя. Связь: извлечение → корреляция с тем же именем переменной в более позднем запросе, либо общий датасет. Реализация: `frontend/lib/grouping.ts` и зеркала в генераторах. Если зеркало разъедется, портал покажет одну группу, а скрипт поедет другим составом.

## Идентификаторы после сохранения

```
build_id → script_id → run_id → analysis_id
                test_id (Jira) висит на прогоне
```

`test_id` вводит пользователь при запуске. В GitLab он уходит как `RUN_ID`. `run_id` — id строки `test_runs`, в webhook это `PORTAL_RUN_ID`.
